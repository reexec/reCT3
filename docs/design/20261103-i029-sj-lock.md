# 설계: CRI SJ 임계 구역의 호스트 잠금 — 음악 반복의 원인 (issue #29)

상태: 구현됨([작업 지시](../work-orders/20261027-i029-adxm-lock.md) §후속, [작업 로그](../work-logs/20261027-i029-adxm-lock.md)). 분석: [cri-middleware](../analysis/cri-middleware.md) §4. 이전 설계: [i029 ADXM 잠금](20261027-i029-adxm-lock.md).

## 1. 원인 (**확인됨**)

* 데모에서 재현된 순간의 게스트 메모리(`REXBOX_STALL_DUMP`, rexbox #43의 보고)를 보면 음악의 출력 SJ 링 두 개(`0x3448D0`, `0x344900`)는 가득 차 있다. 입력 SJ 링(`0x3448A0`, 0x28000바이트)은 빈 공간(0xCCA0)과 데이터(0x3AC)를 합해도 전체에서 약 108 KB가 모자란다. 진행 중인 읽기는 0x1000바이트뿐이다.
* SJ 링 함수(SJRBF GetChunk·PutChunk 등)는 모두 `0x000BC950`에 들어가고 `0x000BC970`으로 나온다. 이 빌드에서 둘은 전역 `[0x2E05F0]`만 만지는 빈 임계 구역이다. Xbox 단일 코어에서는 CRI 서버가 겹치지 않았기 때문이다.
* `PutChunk`(`0x000B8120`)는 돌려받은 조각이 레인 위치와 이어지지 않으면 오류 −3을 알리고 조각을 버린다. 그 바이트는 링에서 사라진다.
* 호스트에서는 파일 서버 스레드(`0x000B3520`, 읽은 데이터를 입력 링에 넣음)와 ADX 서버(vsync 스레드, 입력 링에서 꺼내 디코드)가 같은 링의 수와 위치를 동시에 고친다. 그래서 링이 바이트를 잃고, 남은 것이 모자라면 스트림이 멈춘다. DirectSound 버퍼는 마지막 0.34초를 반복한다.

## 2. 설계

`src/game/ct3/decomp/sj_lock.c`: `sub_000BC950`은 rexbox 게스트 잠금 "CRI SJ lock"을 잡고 lift 본문을 실행한다. `sub_000BC970`은 lift 본문을 실행하고 잠금을 놓는다. 게스트 잠금은 스레드마다 재귀다. SJ 구역 안에서는 SJ 코드만 돌고 ADXM 잠금을 잡지 않으므로, ADXM 잠금과의 순서 문제는 없다. 게임 로직은 바꾸지 않는다.

## 3. 검증

숨김 데모 400초 3개를 동시에 돌린다. 수정 전 빌드는 3개 모두 재현됐다(보고 5회). 수정 빌드는 재현 0회. 그다음 사용자 플레이로 확인한다.

# Design: a host lock for CRI's SJ critical section, the cause of the music repeat (issue #29)

Status: implemented ([work order](../work-orders/20261027-i029-adxm-lock.md), follow-up; [work log](../work-logs/20261027-i029-adxm-lock.md)). Analysis: [cri-middleware](../analysis/cri-middleware.md) section 4. Earlier design: [i029 ADXM lock](20261027-i029-adxm-lock.md).

Cause (**confirmed**): the guest memory at a demo reproduction (`REXBOX_STALL_DUMP` with rexbox #43's report) shows the music's two output SJ rings (`0x3448D0`, `0x344900`) full and its input SJ ring (`0x3448A0`, 0x28000 bytes) about 108 KB short of its size counting free space (0xCCA0) and data (0x3AC), with only a 0x1000-byte read in flight. Every SJ ring function (the SJRBF GetChunk, PutChunk and friends) enters `0x000BC950` and leaves through `0x000BC970`, an empty critical section in this build (they only touch the global `[0x2E05F0]`) because the CRI servers never overlapped on the Xbox's single core. `PutChunk` (`0x000B8120`) reports error −3 and drops a returned chunk that no longer meets the lane's position, and those bytes leave the ring. On the host the file server thread (`0x000B3520`, filling the input ring after each read) and the ADX server (the vsync thread, taking from it to decode) update one ring's counts and positions in parallel, the ring loses bytes, and once too few are left the stream stops and the DirectSound buffer replays its last 0.34 s.

Design: `src/game/ct3/decomp/sj_lock.c`: `sub_000BC950` takes the rexbox guest lock "CRI SJ lock" and runs the lifted body; `sub_000BC970` runs the lifted body and releases it. The guest lock is recursive per thread; only SJ code runs inside the section and it takes no ADXM lock, so there is no ordering issue with the ADXM lock. Game logic is unchanged.

Verification: three hidden 400 s demos run in parallel: the build without the fix reproduced in all three (five reports), the fixed build in none; then user play.
