# 설계: Linux x64 / x86 빌드와 첫 실행 (issue #25)

## 1. 요구사항

게임을 Linux x64와 Linux x86에서 빌드하고 실행한다. 먼저 WSL2(Ubuntu 24.04, WSLg)에서, 그다음 Linux 실기에서 한다. rexbox는 v0.0.2부터 Linux에서 빌드되고 probe가 통과하지만(설계 i004), 그 Linux 플랫폼 계층 위에서 타이틀이 돈 적은 없고, lifted 코드가 GCC로 컴파일되거나 64비트 호스트에서 실행된 적도 없다.

## 2. 현재 구조

* rexbox: `CMakePresets.json`(`linux-{x64,x86}-{debug,release}`, Ninja), `scripts/build_linux.sh`, POSIX 플랫폼 계층(SDL3). x86은 `-m32`에 `-msse2 -mfpmath=sse`.
* reCT3: Win32 전용 빌드 스크립트(`scripts/build_win32_x86.ps1`)만 있다. `src/app/CMakeLists.txt`의 MSVC 전용 링크 옵션은 `if(MSVC)` 안에 있고, `main.cpp`는 `_WIN32`/`__ANDROID__`/그 밖으로 나뉜다.
* 생성 코드(`gen/ct3_jp/gen`)는 플랫폼 중립 C다. 게스트 주소는 `XBOX_PTR(addr) = (uintptr_t)(uint32_t)addr + g_xbox_mem_offset`로 호스트 포인터가 되므로 64비트 호스트에서도 같은 코드가 쓰인다.

## 3. 설계

* reCT3에 rexbox와 같은 모양의 `CMakePresets.json`과 `scripts/build_linux.sh`를 둔다. 빌드 트리는 `build/linux-<arch>-<config>`이고, `RECT3_BUILD_DIR`이 있으면 그 아래에 둔다(WSL2에서 `/mnt` 아래 트리는 9p 때문에 느리다).
* 생성 코드는 Windows에서 만든 것을 그대로 쓴다(`gen/`은 저장소에 없으므로 같은 작업 트리를 `/mnt/e`로 쓴다). Linux에서 `regenerate.py`를 돌리는 것은 이 issue의 범위 밖이다.
* 실행은 `REXBOX_DISPLAY=hidden REXBOX_AUDIO=none`으로 어트랙트 데모까지, 그다음 WSLg 창으로 한다. HDD 루트는 실행 디렉터리의 `hdd/`이므로 Linux 쪽 캐시는 따로 만들어진다.
* rexbox를 바꿔야 하면 rexbox issue로 한다. 이번에는 v0.0.14(GNU ld 링크 순서, 생성 코드 없는 트리)가 이미 그 몫을 한다.

### 위험

* 64비트 호스트: lifted 코드의 포인터 가정(**미확정** → 실행으로 확인).
* WSL2: OpenGL이 llvmpipe(소프트웨어)이고 soft-dirty 페이지 추적이 없어 D3D8이 버퍼를 모두 비교한다. fps 수치는 실기와 다르다.
* `/mnt/e`의 디스크 자산 읽기(9p)가 느려 캐시 생성과 데모 시작이 늦을 수 있다.

## 4. 검증

* x64·x86 Release 빌드 오류·경고 0, CTest 6/6.
* 숨김 실행 100초: 멈춤·`no target`·stall 없이 3D 데모(draws 수백)까지. 프레임 덤프로 Win32와 비교.
* WSLg 창 실행(표시·오디오·입력)은 사용자가 확인한다.


## 5. 후속: Linux 실기와 Linux에서의 생성 (2026-10-27)

* `regenerate.py`를 Linux에서 돌린다. 파이프라인은 이미 Python과 xboxrecomp 도구뿐이라 플랫폼 중립이고, 막힌 곳은 `rexbox_xdk_symbols`를 찾는 후보 경로가 Win32 트리뿐이라는 점이다. 후보에 Linux 프리셋 트리(`build/linux-<arch>-<config>`, `RECT3_BUILD_DIR`이 있으면 그 아래도)를 더한다. `lifter.py`와 rexbox는 바꾸지 않는다.
* `scripts/build_linux.sh`는 git에 실행 권한(100755)으로 둔다. 지금은 100644라 받은 그대로는 `scripts/build_linux.sh`로 실행되지 않는다.
* 가이드는 Linux 실기를 기본 경로로 다시 쓴다(apt 패키지와 `python3-capstone`, 저장소, `roms/`, 도구 빌드, 생성, 빌드, 실행). WSL2는 한 절로 줄인다. README에 Linux 빌드 절을 둔다.
* 검증: 실기에서 생성, 빈 트리의 x64 Release 빌드와 CTest, 숨김 실행 100초. x86은 실기에 i386 패키지가 갖춰지면 같은 절차로 한다.

## 6. 후속: 실기의 x86 빌드와 실행 (2026-11-10)

실기(Ubuntu 26.04, NVIDIA 595.99.02, Wayland 세션)에서 x86을 처음 빌드하고 돌리며 두 가지 환경 문제가 확인됐다. 둘 다 우리 코드나 rexbox 코드의 결함이 아니다.

1. **`libxtst-dev:i386`이 설치되지 않는다.** 2:1.2.5-1ubuntu0.1의 i386 판과 amd64 판은 같은 버전인데, 서로 다른 docbook-xsl로 생성된 man 페이지 11개(`/usr/share/man/man3/XTest*.3.gz`)를 담는다. `Multi-Arch: same` 패키지의 공유 파일이 달라서 dpkg가 `trying to overwrite shared ... which is different from other instances`로 거부한다. 헤더는 두 판이 같다. 설치하지 않으면 SDL3 configure가 `XTEST`에서 멈춘다.
2. **x86 빌드가 Wayland에서 창을 열지 못한다.** `[d3d8] cannot open the display: SDL_CreateWindow failed: unable to create an EGL window surface`가 나고, 화면 없이 게임이 진행된다(draws 0). NVIDIA EGL 외부 플랫폼 중 우선순위가 가장 높은 `libnvidia-egl-wayland2.so.1`(09_nvidia_wayland2.json)의 i386 판에서 `eglCreateWindowSurface`가 실패한다. 같은 모듈의 x64 판과, 구형 `libnvidia-egl-wayland.so.1`(1.1.21)의 i386 판은 성공한다. X11 드라이버(XWayland)도 성공한다.

결정:

* 코드는 바꾸지 않고 가이드에 증상과 우회를 적는다. ① `sudo apt-get -o Dpkg::Options::=--force-overwrite install libxtst-dev:i386`(man 페이지만 덮어쓴다). ② x86을 NVIDIA의 Wayland 세션에서 돌릴 때는 `SDL_VIDEO_DRIVER=x11`.
* rexbox의 `display_sdl`이 Wayland에서 실패하면 x11로 다시 여는 자동 폴백은 이번에 하지 않는다. 드라이버 한 판의 결함에 런타임 경로를 더하는 것이고, 환경 변수 하나로 충분하다. 같은 증상이 다른 환경에서도 나오면 rexbox issue로 다시 검토한다.
* rexbox 가이드는 고치지 않는다. 그 가이드는 게임 실행을 다루지 않고, i386 목록에 `libxtst-dev:i386`이 없다.
* 검증: 실기에서 `regenerate.py`, x64·x86 Release 빌드와 CTest, x64 숨김 실행 100초, x86 숨김 실행 100초(`SDL_VIDEO_DRIVER=x11`). 세 실험(기본, wayland2만, 구형 wayland만)으로 실패 모듈을 가린다.

# Design: Linux x64 / x86 build and first run (issue #25)

## 1. Requirement

Build and run the game on Linux x64 and Linux x86, first on WSL2 (Ubuntu 24.04, WSLg), then on a Linux machine. rexbox has built on Linux with passing probes since v0.0.2 (design i004), but no title has run on its Linux platform layer, and the lifted code has never been compiled by GCC or run on a 64-bit host.

## 2. Current structure

rexbox has `CMakePresets.json` (`linux-{x64,x86}-{debug,release}`, Ninja), `scripts/build_linux.sh` and a POSIX platform layer (SDL3); x86 is `-m32` with `-msse2 -mfpmath=sse`. reCT3 has only the Win32 build script; the MSVC-only link options in `src/app/CMakeLists.txt` sit under `if(MSVC)`, and `main.cpp` branches on `_WIN32`/`__ANDROID__`/else. The generated code (`gen/ct3_jp/gen`) is platform-neutral C: a guest address becomes a host pointer through `XBOX_PTR(addr) = (uintptr_t)(uint32_t)addr + g_xbox_mem_offset`, so the same code serves a 64-bit host.

## 3. Design

reCT3 gets a `CMakePresets.json` and `scripts/build_linux.sh` of rexbox's shape; the tree is `build/linux-<arch>-<config>`, or under `RECT3_BUILD_DIR` when set (on WSL2 a tree under `/mnt` is slow over 9p). The generated code made on Windows is used as it is (`gen/` is not in the repository, so the same working tree is used through `/mnt/e`); running `regenerate.py` on Linux is outside this issue. Runs go hidden with no audio to the attract demo, then in a WSLg window; the HDD root is `hdd/` under the run directory, so Linux builds its own cache. A change rexbox needs goes through a rexbox issue; this time v0.0.14 (GNU ld link order for a tree without generated code) already covers it.

Risks: the lifted code's pointer assumptions on a 64-bit host (**unresolved**, settled by running); on WSL2 OpenGL is llvmpipe (software) and there is no soft-dirty page tracking, so D3D8 compares whole buffers and fps differs from a real machine; disc asset reads over `/mnt/e` (9p) are slow, delaying cache building and the demo.

## 4. Verification

x64 and x86 Release with 0 errors and warnings and CTest 6/6; a hidden 100 s run reaching the 3D demo (hundreds of draws) with no stop, `no target` or stall, compared with Win32 by frame dumps; a WSLg window run (display, audio, input) checked by the user.

## 5. Follow-up: a Linux machine and generation on Linux (2026-10-27)

`regenerate.py` runs on Linux. The pipeline is already only Python and xboxrecomp's tools, so it is platform-neutral; what blocks it is that the candidate paths for `rexbox_xdk_symbols` are the Win32 tree only. The Linux preset trees (`build/linux-<arch>-<config>`, and under `RECT3_BUILD_DIR` when set) join the candidates; `lifter.py` and rexbox are unchanged. `scripts/build_linux.sh` is kept executable in git (100755); at 100644 a fresh checkout cannot run it as `scripts/build_linux.sh`. The guide is rewritten with a Linux machine as the main path (apt packages with `python3-capstone`, repository, `roms/`, the tool build, generation, build, run), WSL2 shrinking to one section, and README gains a Linux build section. Verification: on the machine, generation, a fresh-tree x64 Release build with CTest, and a hidden 100 s run; x86 follows the same steps once the machine has the i386 packages.

## 6. Follow-up: the x86 build and run on the machine (2026-11-10)

Building and running x86 on the machine (Ubuntu 26.04, NVIDIA 595.99.02, a Wayland session) for the first time shows two problems of the environment, neither a defect of this code or rexbox's. (1) **`libxtst-dev:i386` does not install.** The i386 and amd64 packages of 2:1.2.5-1ubuntu0.1 are the same version but carry eleven man pages (`/usr/share/man/man3/XTest*.3.gz`) generated by different docbook-xsl versions; a `Multi-Arch: same` package's shared files differ, so dpkg refuses with `trying to overwrite shared ... which is different from other instances`. The headers are identical. Without the package SDL3's configure stops at `XTEST`. (2) **The x86 build cannot open a window on Wayland.** `[d3d8] cannot open the display: SDL_CreateWindow failed: unable to create an EGL window surface` is logged and the game runs without a picture (0 draws). The i386 build of NVIDIA's highest-priority EGL external platform, `libnvidia-egl-wayland2.so.1` (09_nvidia_wayland2.json), fails `eglCreateWindowSurface`; the x64 build of the same module and the i386 build of the older `libnvidia-egl-wayland.so.1` (1.1.21) succeed, and so does the X11 driver (XWayland).

Decision: no code changes; the guide records the symptoms and the workarounds, (1) `sudo apt-get -o Dpkg::Options::=--force-overwrite install libxtst-dev:i386` (only the man pages are overwritten) and (2) `SDL_VIDEO_DRIVER=x11` for x86 in an NVIDIA Wayland session. An automatic fallback in rexbox's `display_sdl` (reopening with x11 after a Wayland failure) is not done now: it would add a runtime path for one driver release's defect, and one environment variable is enough; it is reconsidered as a rexbox issue if the symptom appears elsewhere. rexbox's guide is unchanged: it does not cover running a game and its i386 list has no `libxtst-dev:i386`. Verification: on the machine, `regenerate.py`, the x64 and x86 Release builds with CTest, a hidden 100 s x64 run and a hidden 100 s x86 run (`SDL_VIDEO_DRIVER=x11`); three experiments (default, wayland2 only, the older wayland only) single out the failing module.
