# 작업 로그: CRI ADXM 잠금과 SJ 임계 구역 — 음악 반복의 원인 (issue #29)

작업 지시: [20261027-i029-adxm-lock](../work-orders/20261027-i029-adxm-lock.md) · 설계: [20261027-i029-adxm-lock](../design/20261027-i029-adxm-lock.md) · 분석: [cri-middleware](../analysis/cri-middleware.md)

## 한 일

1. 증상: Linux x64 실기(Ubuntu 26.04, RTX 4090)에서 플레이 중 음악이 한 구간을 반복한다. 화면은 정상이고, Windows에서는 정상이었다(사용자 보고). 그때 프로세스에는 CPU 100%로 도는 게스트 스레드가 하나 있었다(자발적 문맥 전환 2회, 비자발적 11,275회).
2. 배제한 것: PipeWire 주기는 512 프레임으로 Windows와 비슷하다. 경로 대소문자는 rexbox VFS가 모든 호스트에서 무시한다.
3. 음악이 CRI ADX(`ADX0.AFS`, ADXXB 1.38)인 것을 확인했다. lift 코드에서 reJSRF와 같은 ADXM 잠금(`000B2FF0`, `000B3030`, `000BB9C0`, `ADXM_SetupThrd` `000B3230`)을 찾았다.
4. reJSRF의 어댑터를 CT3 주소로 옮겨 `src/game/ct3/decomp/adxm_lock.c`를 만들었다. 다른 스레드가 가진 동안 들어오려는 경우의 보고를 더했다.
5. 재생성(`sub_000B2FF0_gen`, `sub_000B3030_gen`), Linux x64 Release 빌드 경고 0, CTest 7/7.
6. 데모 숨김 실행 150초(`REXBOX_DISPLAY=hidden REXBOX_AUDIO=none`): 멈춤·시한 보고 없이 워치독까지 돌았다. 3D 데모는 51~60 fps로 이전과 같았다. 다음 두 보고가 나왔다.
   * `[adxm lock] a thread asked for the lock while another held it; it waits (host exclusion)`: 경합이 실제로 일어난다.
   * `[adxm lock] a thread left the lock at priority 15; its own -2 restored`: 원본의 전역 저장 우선순위가 섞였다.
7. (2026-10-29) main(v0.0.14) 위로 rebase한 뒤 Win32: 재생성, x86 Release 빌드(생성 코드의 기존 D9025 플래그 경고뿐), CTest 7/7. 숨긴 창, 소리 켬으로 데모 150초: 멈춤 없이 돌았고 57~59 fps(3D 구간 52~58). 경합 보고(`asked for the lock while another held it`)가 Linux와 같이 나왔다. 우선순위 복원 보고는 이 실행에서 나오지 않았다.

## 사용자 플레이와 진단 (2026-10-28)

어댑터를 넣어도 플레이 중 음악 반복이 재현됐다. 로컬 진단 코드(커밋하지 않음)로 다음을 확인했다.

1. 음악 출력은 48 kHz 스테레오 PCM 루프 버퍼(65,536바이트, 한 바퀴 0.34초)다. 반복이 시작되면 이 버퍼가 실제 음악을 담은 채 116바퀴 넘게 바뀌지 않는다. 버퍼 바퀴마다 내용 해시를 비교해 확인했다(**확인됨**). 데모에서 바뀌지 않던 22,050 Hz 버퍼는 상수 샘플 `0xFFEF`로 채워진 곡 사이 무음이라 다른 경우다.
2. 같은 순간에 `ADX0.AFS` 읽기(thread 8, 파일 서버 `000B3520` → `000B35F0` → `000B9860`)가 멈추고 다시 시작하지 않는다. 멈춘 위치는 곡(AFS 항목 3) 가운데이고, 같은 곡은 4분 전 같은 위치를 문제없이 지났다. 그래서 데이터 때문이 아니라 타이밍 문제로 **추정**한다.
3. 그때 모든 게스트 스레드는 살아 있다. 파일 서버 플래그 `[0x2E0588]`는 0이고 서버는 매 vblank 돈다. 스트림 상태가 진행하지 않는 것이다.
4. 오디오 장치 요청은 항상 512 프레임으로 고르게 왔다. 장치 쪽이 원인이라는 근거는 없다.
5. CRI 서버는 세 스레드에서 돈다. vsync 스레드(thread 6)가 레벨 2 서버(`000B35E0`, `000C59D0`), mwidle 스레드(thread 7)가 레벨 5 서버(`000C5C50`), thread 8이 파일 서버를 돌린다. Xbox에서는 단일 코어라 한 번에 하나였다.
6. 시험: SVM 서버 실행기(`000B94E0`)와 파일 서버(`000B9860`)도 같은 게스트 잠금으로 감쌌다. 서버 실행이 겹치는 경우가 실제로 있었다는 보고가 나왔다. 오래 플레이해도 괜찮다가 끝에 재현됐는데, 이때는 thread 6이 ADX 서버(`000B35E0` → `000B1AE0` → `000B5060` → `000B4A70` → …) 안에서 HLE 호출 없이 14초 넘게 돌면서 잠금을 쥐고 있었다. 그동안 thread 8과 게임 메인 스레드가 2초 시한까지 기다렸다. 부작용이 있어 이 시험은 반영하지 않았다.
7. 정확한 루프 위치는 잡지 못했다. gdb로 실행하면 재현되지 않았다.

## 기본 로그의 진단 (2026-11-03)

음악 반복이 자주 재현되어, 진단 빌드 없이 평소 로그로 근거를 얻도록 rexbox #43(v0.0.19)에 스트림 정지 보고를 넣었다. 스트림으로 쓰이던 루프 버퍼가 실제 소리를 담은 채 8바퀴, 2초 넘게 바뀌지 않으면 `[dsound] buffer ... its writer stopped` 한 줄을 남긴다. 이어서 게스트 스레드 상태와 호스트 콜스택(Linux)을 출력한다.

* 어트랙트 데모에서도 재현된다(**확인됨**). 숨김 실행 약 143초에 48 kHz 음악 버퍼(`03FDA400`)가 보고됐다.
* 그 순간 모든 게스트 스레드는 평소의 대기에 있었다. thread 6(vsync, `sub_000B3110`)와 thread 8(파일 서버 루프, `sub_000B3520`)은 vblank 대기, thread 7(mwidle)은 자기 정지, thread 2(게임)는 vblank 대기였다. 루프에 갇힌 스레드는 없다. 스트림 상태가 진행하지 않는 것으로, play2와 같다.
* 데모에서 재현되므로 다음 분석은 플레이 없이 데모로 할 수 있다.

## 원인: SJ 임계 구역 (2026-11-03)

1. 플레이 로그(v0.0.17)에서 약 75초에 보고가 나왔다. 호스트 콜스택은 데모와 같아서, 모든 스레드가 평소 대기 중이었다.
2. 데모 재현 순간의 게스트 메모리를 덤프했다. ADX 핸들 `0x34DFC0`(재생 중, 파일 스트림 `0x349480`), 출력 SJ 두 개는 가득 차 있었다. 입력 SJ(`0x3448A0`, 0x28000)는 빈 공간 0xCCA0와 데이터 0x3AC를 합해 약 108 KB가 모자랐고, 진행 중인 읽기는 0x1000뿐이었다.
3. SJ 링 함수는 모두 `0x000BC950`/`0x000BC970`(빈 임계 구역)으로 감싸여 있다. `PutChunk`(`0x000B8120`)는 위치가 어긋난 조각을 오류 −3으로 버린다. 파일 서버와 ADX 서버가 같은 링을 동시에 고쳐 바이트가 새는 것이 원인이다([설계](../design/20261103-i029-sj-lock.md)).
4. `src/game/ct3/decomp/sj_lock.c`로 두 지점을 rexbox 게스트 잠금 "CRI SJ lock"으로 감쌌다. 재생성, Linux x64 Release 빌드 경고 0, CTest 7/7.
5. 대조 실험(숨김 데모 400초 3개를 동시에):

| 빌드 | 재현한 실행 | 보고 |
|---|---|---|
| 수정 전 | 3/3 | 5회 |
| SJ 잠금 | 0/3 | 0회 |

6. 앞서 시험했던 "서버 실행도 잠그기"(반영하지 않음)는 이 경합의 일부를 우연히 막았던 것으로 본다(**추정**).

## 남은 것

* 사용자 플레이로 음악 반복이 사라졌는지 확인한다.
* 사용자 플레이(Win32)에서 음악이 이전과 같은지.

# Work log: the CRI ADXM lock and the SJ critical section, the cause of the music repeat (issue #29)

Work order: [20261027-i029-adxm-lock](../work-orders/20261027-i029-adxm-lock.md) · Design: [20261027-i029-adxm-lock](../design/20261027-i029-adxm-lock.md) · Analysis: [cri-middleware](../analysis/cri-middleware.md)

Symptom: during play on a Linux x64 machine (Ubuntu 26.04, RTX 4090) the music repeats one section while the picture is normal; Windows was fine (user report). The process then had one guest thread at 100% CPU (2 voluntary and 11,275 involuntary context switches). Ruled out: the PipeWire quantum is 512 frames, close to Windows; path case is ignored by rexbox's VFS on every host. The music was confirmed to be CRI ADX (`ADX0.AFS`, ADXXB 1.38), and the lifted code has reJSRF's ADXM lock (`000B2FF0`, `000B3030`, `000BB9C0`, `ADXM_SetupThrd` `000B3230`). reJSRF's adapter was ported to CT3's addresses as `src/game/ct3/decomp/adxm_lock.c`, with a report for a thread asking while another holds the lock. Regenerated (`sub_000B2FF0_gen`, `sub_000B3030_gen`); the Linux x64 Release build has 0 warnings and CTest passes 7/7. A hidden 150 s demo run (`REXBOX_DISPLAY=hidden REXBOX_AUDIO=none`) reached the watchdog with no stop or timeout report, the 3D demo at 51–60 fps as before, and printed `[adxm lock] a thread asked for the lock while another held it; it waits (host exclusion)` (the contention is real) and `[adxm lock] a thread left the lock at priority 15; its own -2 restored` (the original's global saved priority got mixed).

On 2026-10-29, after rebasing onto main (v0.0.14), Win32: regenerated; the x86 Release build has only the generated code's existing D9025 flag warnings; CTest 7/7. A hidden demo run with audio on went 150 s without a stop at 57–59 fps (52–58 in 3D) and printed the same contention report as Linux (`asked for the lock while another held it`); the priority-restore report did not appear in this run.

User play and diagnosis (2026-10-28): with the adapter the music still repeated during play. Local diagnostics (not committed) showed that the music output is a 48 kHz stereo PCM loop buffer (65,536 bytes, 0.34 s a lap), and once the repeat starts it keeps real music unchanged for over 116 laps (lap content hashes, **confirmed**); the unchanged 22,050 Hz buffer of the demo is a different case, silence between tracks filled with the constant sample `0xFFEF`. At the same moment the `ADX0.AFS` reads (thread 8, the file server `000B3520` → `000B35F0` → `000B9860`) stop for good, in the middle of a track (AFS entry 3) whose same position passed fine four minutes earlier, so timing rather than data is **inferred**. Every guest thread is alive then, the file server flag `[0x2E0588]` is 0 and the server runs every vblank: the stream state does not advance. The device always asked for an even 512 frames, so nothing points at the device. The CRI servers run on three threads: the vsync thread (thread 6) runs the level-2 servers (`000B35E0`, `000C59D0`), the mwidle thread (thread 7) the level-5 server (`000C5C50`), thread 8 the file server; on the Xbox's single core one ran at a time. A trial wrapping the SVM server executor (`000B94E0`) and the file server (`000B9860`) in the same guest lock reported overlapping server passes, and play went well for a long time until a repeat at the end, when thread 6 had been running inside the ADX server (`000B35E0` → `000B1AE0` → `000B5060` → `000B4A70` → …) with no HLE call for over 14 s while holding the lock, thread 8 and the game's main thread waiting up to the 2 s timeout; with that side effect the trial is not kept. The exact loop was not caught; the game did not reproduce it under gdb.


Default-log diagnosis (2026-11-03): since the repeat recurs often, rexbox #43 (v0.0.19) adds a stalled-stream report so ordinary logs carry the evidence: a loop buffer used as a stream that keeps real sound unchanged for 8 laps and over 2 s gets one `[dsound] buffer ... its writer stopped` line, followed by the guest thread states and host stacks (Linux). The attract demo reproduces it too (**confirmed**): a hidden run reported the 48 kHz music buffer (`03FDA400`) at about 143 s, with every guest thread in its usual wait (thread 6, vsync `sub_000B3110`, and thread 8, the file server loop `sub_000B3520`, in vblank waits; thread 7, mwidle, self-suspended; thread 2, the game, in a vblank wait), none stuck in a loop: the stream state does not advance, as in play2. Since the demo reproduces it, the next analysis needs no play.


The cause, the SJ critical section (2026-11-03): a play log (v0.0.17) reported at about 75 s with host stacks like the demo's, every thread in its usual wait. The guest memory at a demo reproduction showed the ADX handle `0x34DFC0` playing (file stream `0x349480`), its two output SJ rings full, and the input SJ ring (`0x3448A0`, 0x28000) about 108 KB short counting free space 0xCCA0 and data 0x3AC, with only 0x1000 in flight. Every SJ ring function is wrapped in `0x000BC950`/`0x000BC970`, an empty critical section, and `PutChunk` (`0x000B8120`) drops a chunk that no longer meets its lane's position with error −3: the file server and the ADX server updating one ring together leak its bytes ([design](../design/20261103-i029-sj-lock.md)). `src/game/ct3/decomp/sj_lock.c` wraps the two in the rexbox guest lock "CRI SJ lock"; regenerated, Linux x64 Release with 0 warnings, CTest 7/7. A comparison of three hidden 400 s demos run in parallel: without the fix 3/3 runs reproduced (5 reports), with it 0/3 (0). The earlier trial locking the server passes (not kept) presumably blocked part of this race by chance (**inferred**).

Left open: confirming in user play that the music repeat is gone; whether the music is as before in user play on Win32.
