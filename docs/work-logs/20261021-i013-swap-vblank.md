# 작업 로그: 프레임마다 vblank 두 개 — 게임 속도 — 완료 (issue #13)

작업 지시: [20261021-i013-swap-vblank](../work-orders/20261021-i013-swap-vblank.md) · rexbox: issue #18, [작업 로그](../../third_party/rexbox/docs/work-logs/20261021-i018-swap-queues-flip.md)

## 한 일

1. 시계 확인: `KeTickCount`(벽시계 ms)와 rdtsc(733 MHz)는 정확했다. vblank 스레드(`0x2DFDA8`)와 `sub_000B3180` 루프(`0x2DFDAC`)도 초당 60회였다.
2. 측정: 운전 화면의 game time이 frame 2400에 43, 3000에 33, 3600에 23이었다. **present 하나에 게임 시간 1/60초**다. 그래서 fps가 60보다 낮은 만큼 게임이 느리다. issue #11에서 "로직 60 Hz, 화면 30 fps, 속도 정상"으로 본 것은 틀렸다. 60 Hz 루프는 게임 로직이 아니다.
3. 원인: 타이틀 화면이 프레임당 CPU 0.47 ms인데 29.5 fps(`wait` 32 ms)였다. HLE 추적에서 프레임 끝은 `D3DDevice_Swap(0)` → `D3DDevice_BlockUntilVerticalBlank()`(`000A7085`~`000A708C`)였다. rexbox의 `Swap`이 vblank까지 잠들고 타이틀이 한 번 더 기다려 프레임마다 vblank 두 개가 걸렸다.
4. rexbox #18: `Swap`은 플립을 예약하고 돌아오며, 앞 플립이 대기 중일 때만 기다린다. submodule을 작업 브랜치 커밋 `97dcae3`로 올렸다.
5. 분석 문서 §7의 프레임 구조 항목을 바로잡았다(`0x2C2800`의 뜻 포함).

## 검증

| 검증 | 결과 |
|---|---|
| Win32 x86 Release, CTest | 오류 0, 5/5 |
| 타이틀 화면 | 29.5 fps → 창·vsync 60.0~60.1, 숨김 60.0, vsync 끔 60.0 |
| 데모 도시 장면(300프레임 구간) | 22.4~24.2 fps → 39.7~41.6 fps |
| 운전(같은 입력 스크립트, `REXBOX_HLE_FALLBACK=lifted`) | game time 31 → 21에 41.8초(14.4 fps, 실시간의 0.24배) → 28 → 08에 62.9초(19.1 fps, 0.32배) |

## 남은 것

* 이 기계(i5-7200U, 2코어)에서는 운전 화면의 CPU가 프레임당 33~40 ms라 아직 실시간보다 느리다. 게임 속도는 fps/60이므로, 프레임 시간을 줄이는 일(D3D8 `setup`, 타이틀 코드의 "other" 19~23 ms)이 다음이다.
* 게임 시작(Start)은 아직 `D3DDevice_InsertFence`(`000F5050`)에서 멈춘다. 이번 운전 검증은 `REXBOX_HLE_FALLBACK=lifted`로 했다.

# Work log: two vblanks per frame — the game's speed — done (issue #13)

Work order: [20261021-i013-swap-vblank](../work-orders/20261021-i013-swap-vblank.md) · rexbox: issue #18, [work log](../../third_party/rexbox/docs/work-logs/20261021-i018-swap-queues-flip.md)

Done:

1. The clocks were checked. `KeTickCount` (wall-clock ms) and rdtsc (733 MHz) are right, and the vblank thread (`0x2DFDA8`) and the `sub_000B3180` loop (`0x2DFDAC`) run 60 times a second.
2. The in-game game time while driving read 43 at frame 2400, 33 at 3000 and 23 at 3600: **1/60 s of game time per present**, so the game slows by as much as fps falls short of 60. Issue #11's "logic at 60 Hz, picture at 30 fps, speed correct" was wrong: the 60 Hz loop is not the game logic.
3. The cause: the title screen ran at 29.5 fps (`wait` 32 ms) on 0.47 ms of CPU per frame. An HLE trace shows each frame ending with `D3DDevice_Swap(0)` → `D3DDevice_BlockUntilVerticalBlank()` (`000A7085`–`000A708C`). rexbox's `Swap` slept to the vblank and the title then waited again, so every frame took two vblanks.
4. rexbox #18: `Swap` queues the flip and returns, waiting only while the previous flip is pending. The submodule moved to the task branch's commit `97dcae3`.
5. The frame-structure entry in analysis section 7 was corrected, including what `0x2C2800` means.

Verification:

| Check | Result |
|---|---|
| Win32 x86 Release, CTest | no errors, 5/5 |
| Title screen | 29.5 fps → 60.0–60.1 in a window with vsync, 60.0 hidden, 60.0 with vsync off |
| Demo city scenes (300-frame spans) | 22.4–24.2 fps → 39.7–41.6 fps |
| Driving (same input script, `REXBOX_HLE_FALLBACK=lifted`) | game time 31 → 21 in 41.8 s (14.4 fps, 0.24× real time) → 28 → 08 in 62.9 s (19.1 fps, 0.32×) |

Left over:

* On this machine (i5-7200U, two cores) driving takes 33–40 ms of CPU per frame, so the game is still slower than real time. Game speed is fps/60, so the next step is cutting frame time (D3D8 `setup`, and the title code's "other" at 19–23 ms).
* Starting a game (Start) still stops at `D3DDevice_InsertFence` (`000F5050`); the driving check ran with `REXBOX_HLE_FALLBACK=lifted`.
